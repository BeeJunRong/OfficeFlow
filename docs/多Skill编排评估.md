## 1. 四个 Skill 不是一条链，而是"一对多、分方向"的图

这是本次评估最关键的一点。"做完一个就把剩下的都做一遍"假设它们能排队，但实际数据依赖是这样的：

| 源 → 目标 | 成立 | 依据 |
|---|---|---|
| 会议纪要 → 周报整理 | ✅ | 会议的待办/决定正是周报素材 |
| 会议纪要 → 邮件草稿 | ✅ | 会后通知邮件；收件人可从待办负责人推 |
| 会议纪要 → 网页整理 | ❌ | **会议记录里没有网页，没有输入源** |
| 周报整理 → 邮件草稿 | ✅ | 周报本身可发邮件 |
| 网页整理 → 会议纪要 | ❌ | 方向反了 |
| 周报整理 → 会议纪要 | ❌ | 方向反了 |
| 邮件草稿 → 任何 | ❌ | 终端产物，不再派生 |

**推论**：

1. 从"会议纪要"出发，**最多只能派生 2 份**（周报素材、邮件草稿），**网页整理无从下手**——它需要 URL/网页文本作为输入，会议记录里没有。
2. 从"网页整理"出发，**什么都派生不出来**。
3. 所以正确的模型不是"线性链"，而是**"同一份输入 → 多个产物"**（广播），或**"当前产物 → 派生建议"**（有向图）。

## 2. 三种可能的做法与可行性

### 理解 A：一次输入，同时产出多份（广播）

```text
粘贴一次会议记录
   ↓
勾选：☑会议纪要  ☑周报素材  ☑邮件草稿
   ↓
【一次抽取】决定 / 待办 / 负责人 / 截止日期      ← 关键：只抽一遍
   ↓
分别套模板渲染 → 3 份独立结果，各自可编辑、各自导出
```

- **优点**：只调用一次抽取（省时省钱：13 例样本的 token 消耗不增加）；用户对每份产物都有检查权；不违反"不擅自执行"；验收仍可逐字段比对。
- **可行性**：高。且因为**复用同一次抽取结果**，它是三者里性价比最高的。
- **代价**：响应契约要从"单结果"改成"多结果"，前端与测试跟着改（见 §3）。

### 理解 B：真·自动串联（依次执行）

```text
会议纪要 → [自动] 周报整理 → [自动] 邮件草稿 → 全部塞给用户
```

- **问题 1（合规）**：用户对第二、三份产物的**检查被跳过了**。一旦中途周报或邮件写错，用户可能在没注意的情况下导出。这直接触碰 `guardrails.md` §1 的 Q-02 红线——"不可逆行为人工确认"、"发送、对外分享等操作不由 Agent 擅自执行"。
- **问题 2（范围）**：`proposal.md` §5 明文排除"**多智能体自治协作**"；`architecture.md` §1 也写明"采用**单 Agent + 多工具**架构，**避免多智能体**带来的开发与验收复杂度"。自动串联正是这条排除项。
- **问题 3（无意义执行）**：按 §1 的依赖图，"剩下的都做一遍"里包含**网页整理**，而它没有输入源 → 只会产出一份空洞结果。
- **可行性**：技术可行（LangGraph 加边即可），但**不建议**。

### 理解 C：单向派生 + 用户确认（推荐备选）

```text
会议纪要生成完成
   ↓
界面出现："基于本次纪要，还可以生成 →"
        [ 会后通知邮件草稿 ]  [ 本周周报素材 ]
   ↓
用户点击才执行（复用已抽取的结构化结果，不重新抽取）
```

- **优点**：兼顾"不用一个个手点"和"人工确认"；明确只提供**有依赖依据**的派生项（网页整理不出现）；复用抽取结果，零额外 token。
- **可行性**：中高。改动比 A 小（响应契约不用改成多结果，只需增加"可派生项"字段）。

## 3. 代码影响面（若做理解 A）

### 3.1 必须改的契约

| 文件 | 现状 | 需改成 |
|---|---|---|
| `app/schemas.py` `GenerateResponse` | `structured_result: MeetingMinutes \| None` + `markdown: str` | 新增 `results: list[SkillResult]`（每项含 `task_type` / `structured_result` / `markdown` / `tool_logs` 分段） |
| `app/schemas.py` `AgentState` | `task_type: str`（单个） | 需携带 `task_types: list[str]` 与各产物结果 |
| `app/main.py:87-97` | 组装单个 `structured_result` | 组装 `results[]`；`store.save_result` 需按 skill 分别落库 |
| `app/graph.py:70-79` | `route → execute → END` | `route → execute(并行/串行多 skill) → END` |
| `app/skills/base.py` `Skill.run` | 返回整个 `AgentState` | 契约本身够用，但**多 skill 共用同一 state** 会互相覆盖 `markdown` / `structured_result` —— 需定义"产物容器" |
| `app/tools/export_markdown.py` | 单文件导出 | 多产物需支持分别导出、文件名区分 |

### 3.2 前端改动

| 位置 | 现状 | 影响 |
|---|---|---|
| `frontend/app.py:180` | `if resp["task_type"] == "meeting_minutes":` 才渲染编辑框 + 导出按钮，否则 `st.info(markdown)` | 需改为**遍历 `results[]`**，每份产物各带编辑框与独立导出按钮 |
| `frontend/app.py:213-225` `_task_chips` | 单选（`.locked_task_type: str`） | 需改为**多选**（`locked_task_types: list`），且"自动识别"语义要重新定义 |
| 工具步骤展示 | 单一日志流 | 需按 skill 分组展示，否则 3 份产物的日志会混在一起 |

### 3.3 数据库

`officeflow_logs.db` 现有三张表（`sessions` / `results` / `tool_logs`）。`results` 当前按 `session_id` 存单份结果，多产物需要**加 skill 维度**（否则同 session 的多份结果会互相覆盖）。属 schema 变更，需迁移脚本或容忍旧库。

## 6. 我的建议

**本版不做，先收尾 FR-01。** 理由：

1. **FR-01 尚未完成实测**。核心链路（零编造、导出、重试）只在规则引擎下验证过；配了 API Key 后的 LLM 路径、以及 LangExtract 的**中文对齐质量**都还没验。这是唯一纳入验收的项，风险应在这里清零，而不是在它旁边加变量。
2. **P1 三个 skill 是空壳**。"串联"的收益取决于有没有东西可串——现在串起来只会输出三次"P1 开发中"。
3. **改动性质是"改契约"而非"加功能"**。响应结构、前端渲染、测试断言、DB schema 全要动，而验收体系是按单产物设计的。

**如果确实要推进**，建议顺序：

1. **先做理解 A 的最小切片**：「会议纪要 → 邮件草稿」一对（复用现有结构化输出最充分）。
2. 跑通后再加「→ 周报素材」。
3. **网页整理永远不放进自动派生**（没有输入源，见 §1）。
4. **不要做理解 B**，它会同时触碰 Q-02 与 proposal §5 两条红线。

**若你更在意"少点几下"而非"少写代码"**，理解 C 是折中：改动小于 A（响应契约不用变多结果），且派生项显式列出、用户点击才执行——既省操作又不丢人工确认。
